# 플랫폼 간 화면 동기화

입력: $ARGUMENTS

## 인자

- 첫 단어는 `기준 플랫폼`이다: `ios` 또는 `android`
  - 대소문자를 구분하지 않는다. `iOS`, `IOS`, `Android`, `ANDROID` 모두 소문자로 바꿔 해석한다
  - 둘 중 어느 것도 아니면 멈추고 사용법을 알려 준다
  - `대상 플랫폼`은 기준 플랫폼의 반대쪽이다
- 두 번째 단어는 `화면 종류`와 `화면 이름`을 붙여 쓴 파스칼 케이스 단어다 (예: `Home`, `HomeDetail`, `Journal`, `JournalEditor`)
  - 첫 대문자 단어가 `화면 종류`, 나머지가 `화면 이름`이다
    - `JournalEditor` → 화면 종류 `Journal`, 화면 이름 `Editor`
    - `Home` → 화면 종류 `Home`, 화면 이름 없음
  - 끝에 `View` 나 `Screen` 이 붙어 있으면 떼고 해석한다 (`JournalEditorView` → `JournalEditor`)
- 모드 (생략하면 build 후 verify 둘 다)
  - `build` : 비교와 수정만
  - `verify` : 검증만 (코드를 고치지 않는다)
- `--` 뒤의 문장은 인자가 아니라 이번 실행에만 적용할 `추가 지시`이다
  - 위의 인자 규칙은 `--` 앞부분에만 적용한다. `--` 뒤의 단어는 플랫폼, 화면 이름, 모드로 해석하지 않는다
  - 예: `/sync_platform IOS JournalEditor build -- 사진 영역은 제외` → 기준 ios, 화면 종류 Journal, 화면 이름 Editor, 모드 build, 추가 지시 "사진 영역은 제외"
  - 이 스킬의 규칙과 충돌하면 추가 지시를 따르고, 보고할 때 그 사실을 적는다
  - 검증을 서브에이전트에게 맡길 때 추가 지시 중 검증에 관한 내용은 함께 넘긴다

## 기준

- **기준 플랫폼의 코드가 유일한 기준이다.** `specs/` 폴더의 SCREEN_SPEC.md 와 참고 이미지는 읽지 않는다
- 기준 플랫폼의 코드는 고치지 않는다. 기준 쪽에서 버그나 누락을 발견하면 보고에만 적는다
- 단, 플랫폼 관례에 따른 차이는 맞추지 않고 유지한다 (아래 "유지하는 차이" 참고)

## 프로젝트 설정 (프로젝트에 맞게 수정)

| | iOS (`MPA_ios`) | Android (`MPA_Android`) |
|---|---|---|
| 화면 폴더 | `MPA_ios/MPA_ios/Views/<화면 종류>/` (파스칼 케이스) | `MPA_Android/app/src/main/java/com/example/mpa_android/ui/view/<화면 종류>/` (모두 소문자) |
| 화면 파일 | `<화면 종류><화면 이름>View.swift` | `<화면 종류><화면 이름>Screen.kt` |
| 뷰 모델 | `MPA_ios/MPA_ios/ViewModel/` | `MPA_Android/app/src/main/java/com/example/mpa_android/viewmodel/` |
| 모델 | `MPA_ios/MPA_ios/Model/` | `MPA_Android/app/src/main/java/com/example/mpa_android/model/` |
| DI | — | `MPA_Android/app/src/main/java/com/example/mpa_android/di/` |
| 테스트 | `MPA_ios/MPA_iosTests/` | `MPA_Android/app/src/test/java/com/example/mpa_android/` |
| 진입점·내비게이션 | `MPA_ios/MPA_ios/Views/ContentView.swift` | `MPA_Android/app/src/main/java/com/example/mpa_android/MainActivity.kt` |
| 빌드 | xcodebuild, scheme `MPA_ios` | `./gradlew :app:assembleDebug` |
| 테스트 실행 | `xcodebuild test -scheme MPA_ios` | `./gradlew :app:testDebugUnitTest` |

- iOS 에서 SwiftUI 로 뷰를 만든 파일은 모두 `View` 로 끝난다
- Android 에서 Jetpack Compose 로 뷰를 만든 파일은 모두 `Screen` 으로 끝난다
- 색은 각 플랫폼의 디자인 토큰을 쓴다 (iOS `Color.X`, Android `MPAColor.X.color()`). 기준 쪽 토큰과 같은 이름의 토큰으로 옮긴다

## 0. 준비

1. Bash로 `git rev-parse --show-toplevel` 을 실행해 프로젝트 루트를 확인한다. 이 스킬의 모든 경로는 이 루트 기준이다
2. 인자를 해석하고, 기준·대상 플랫폼, 화면 종류, 화면 이름, 모드, 추가 지시를 한 줄로 사용자에게 알린다
3. 기준 화면 파일을 찾는다
   - 없으면 같은 화면 폴더에서 비슷한 이름을 찾아 후보를 알려 주고 멈춘다
4. 기준 화면이 의존하는 코드를 모은다
   - 화면 파일과 같은 폴더의 하위 뷰 파일
   - 화면이 쓰는 뷰 모델, 모델, 샘플 데이터, 생성기·저장소 프로토콜, DI 모듈
   - 진입점·내비게이션에서 이 화면으로 들어오고 나가는 부분 (어떤 콜백으로 어디로 이동하는지)
   - 이 뷰 모델의 테스트
5. 대상 플랫폼에서 같은 역할의 파일을 찾는다. 없는 파일은 "새로 만듦"으로 표시한다

## 1. 비교와 수정 (build)

### 1-1. 기준 목록 만들기

기준 코드를 읽고 아래 항목별로 목록을 만든다. 이 목록이 비교의 단위다.

- **상태:** 화면이 분기하는 입력값과 상태 (예: 데이터 없음 / 일부 / 충분, AI 가능 / 불가, 로딩 / 실패)
- **구성:** 상태별로 보이는 섹션과 그 순서
- **요소:** 각 섹션의 컴포넌트 종류(카드, 칩, 버튼, 시트, 메뉴, 다이얼로그), 크기, 모서리, 테두리, 간격, 색 토큰, 글꼴 크기·굵기
- **문구:** 화면에 보이는 모든 문자열, 접근성 라벨
- **동작:** 탭, 길게 누르기, 스와이프, 스크롤에 따른 변화, 애니메이션, 햅틱
- **이동:** 각 동작이 여는 화면과 넘기는 값
- **데이터·로직:** 뷰 모델의 계산 규칙, 정렬, 개수 제한, 날짜·시간 형식, 실패 횟수 같은 정책
- **프리뷰:** 기준 쪽 프리뷰 이름과 각 프리뷰가 보여 주는 상태
- **테스트:** 기준 쪽 테스트가 검사하는 규칙

### 1-2. 대상과 비교

- 목록의 항목마다 대상 코드에서 대응하는 부분을 찾아 `일치`, `다름`, `없음` 으로 표시한다
- `다름`, `없음` 은 아래 "유지하는 차이"에 해당하는지 먼저 판단한다
- 비교표를 만든 뒤 수정을 시작한다. 비교표는 보고에 그대로 쓴다

### 유지하는 차이

다음은 플랫폼 관례이므로 맞추지 않는다. 기준 코드나 대상 코드의 주석에 "iOS는 …, Android는 …" 처럼 의도적인 차이가 적혀 있으면 그것도 유지한다.

| 항목 | iOS | Android |
|---|---|---|
| 새 항목 만들기 | 내비게이션 바 trailing 버튼 | Extended FAB |
| 큰 제목 | 본문 헤더 + 스크롤 시 인라인 제목 | Large/Medium Top App Bar (+ subtitle) |
| 메뉴 | contextMenu, Menu | DropdownMenu |
| 경고 | 시스템 Alert | M3 AlertDialog |
| 시트 | `.sheet` + detents | ModalBottomSheet |
| 칩 모양 | 캡슐 | M3 칩 (radius 8) |
| 터치 영역 | 44pt | 48dp |
| 햅틱 | `sensoryFeedback` | `HapticFeedbackConstants` |
| 탭 바 | 플로팅 Liquid Glass 탭 바 | Navigation Bar / Rail |
| 기기 내장 AI 이름 | Apple Intelligence | Gemini Nano |

- 위 표에 없는 차이를 유지하기로 했다면 이유와 함께 보고에 적는다

### 1-3. 대상 수정

- 대상 플랫폼 코드만 고친다. 기준 플랫폼 코드는 고치지 않는다
- 대상 쪽에 없는 모델·뷰 모델·샘플 데이터·DI 는 대상 플랫폼 관례에 맞게 새로 만든다
- 수정·생성한 파일 첫 줄의 주석은 기준 파일과 같게 둔다
  - 기준 파일에 `// [NO AC] Spec: …` 가 있으면 같은 줄을 넣는다
  - 없으면 `// [NO AC]` 를 넣는다
  - 이미 주석이 있는 파일은 그대로 둔다
- 기준 쪽 프리뷰와 **같은 이름**의 프리뷰를 대상 쪽에 만든다. 같은 상태를 같은 mock 데이터로 보여 준다
  - iOS 는 iPhone, iPad 프리뷰를 둘 다 둔다
- 기준 쪽 테스트가 검사하는 규칙을 대상 쪽 테스트로 옮긴다
- 내비게이션 연결(진입점 파일)도 기준과 같은 이동이 되도록 맞춘다. 대상 쪽에 이동할 화면이 아직 없으면 연결하지 않고 보고에 적는다
- 사용자가 작업 중인 것으로 보이는 코드(컴파일되지 않는 줄, TODO, 주석 처리된 블록)는 건드리지 않고 보고에 적는다
- 프로젝트의 CLAUDE.md 규칙(로컬 LLM 위임, 검증 후 반영 등)을 따른다

### 1-4. 빌드와 테스트

- 대상 플랫폼을 빌드한다. 실패하면 고쳐서 다시 빌드하되 최대 3회까지만 시도하고, 그래도 실패하면 멈추고 에러를 보고한다
  - iOS: Xcode MCP `BuildProject` 또는 XcodeBuildMCP, 안 되면 xcodebuild
  - Android: `./gradlew :app:assembleDebug`
- 관련 테스트가 있으면 실행해 통과시킨다
- iOS 는 `RenderPreview` 로 대상 프리뷰를 1차 확인한다. 프리뷰는 한 번에 하나씩 렌더링한다

## 2. 검증 (verify)

검증은 구현한 맥락과 분리하기 위해 **서브에이전트에게 맡긴다.**

서브에이전트에게는 아래만 넘긴다.
- 기준 플랫폼, 대상 플랫폼, 화면 이름
- 기준·대상 화면 파일 경로와 프리뷰 이름 목록
- 검사할 기기·상태 목록
- `추가 지시` 중 검증에 관한 내용 (있을 때만)
- 비교표, 수정 과정, 내가 내린 판단은 넘기지 않는다. 위 "유지하는 차이" 표는 넘긴다

서브에이전트 규칙
- 코드를 수정하지 않는다. 읽기, 빌드, 실행, 스크린샷만 한다
- **기준 플랫폼의 화면을 정답으로 삼는다.** specs 폴더는 보지 않는다
- 같은 상태의 기준 스크린샷과 대상 스크린샷을 한 쌍씩 나란히 비교한다

검사 대상

| 플랫폼 | 기기 | 상태 |
|---|---|---|
| iOS | iPhone Duo 가 아닌 iPhone 시뮬레이터 | 세로 |
| iOS | iPad 시뮬레이터 | 가로 |
| Android | 에뮬레이터 | 세로 |

절차
1. 두 플랫폼 앱을 빌드·실행하고 해당 화면으로 이동한다 (iOS 는 XcodeBuildMCP)
2. 앱에서 만들 수 없는 상태는 프리뷰로 확인한다. 근거가 앱 스크린샷인지 프리뷰인지 적는다
3. 같은 상태끼리 비교한다
   - 섹션 구성과 순서, 간격, 색, 컴포넌트 종류, 모서리, 잘린 요소, 겹침, 문구, 상태별 화면, 동작과 이동
   - "유지하는 차이" 표에 있는 차이는 불일치로 보지 않는다
4. Android는 에뮬레이터가 켜져 있으면 `adb exec-out screencap -p > shot.png` 로 캡처해 비교한다. 꺼져 있으면 건너뛰고 표시한다
5. 사용한 시뮬레이터와 에뮬레이터는 끝나면 종료한다. 시작 전부터 켜져 있던 것은 그대로 둔다

## 3. 보고

아래 순서로 보고한다.

**1) 비교표 (build 를 했을 때)**

| 항목 | 기준 (<기준 플랫폼>) | 대상 수정 전 | 조치 |
|---|---|---|---|

- 조치는 `수정`, `새로 만듦`, `유지(플랫폼 관례)`, `보류` 중 하나다
- `보류`는 이유를 적는다 (예: 대상 쪽에 이동할 화면이 없음)

**2) 검증표**

| 플랫폼 | 기기 | 상태 | 결과 | 불일치 내용 |
|---|---|---|---|---|

- 결과는 `통과`, `불일치`, `수동 확인 필요` 중 하나다
- 불일치는 근거가 된 기준 쪽 코드 위치(파일:줄)나 기준 스크린샷을 함께 적는다

**3) 그 밖에 알릴 것**
- 기준 쪽에서 발견한 버그나 누락 (고치지 않음)
- 표에 없는 이유로 유지한 차이
- 건드리지 않은 사용자 작업 중 코드
- 로컬 LLM 이 맡은 부분과 Claude 가 고친 부분

- 검증에서 나온 불일치 수정은 사용자의 확인을 받은 뒤에 시작한다
